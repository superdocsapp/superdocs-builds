# SuperDocs Latency & Throughput Benchmark

Assigned build (Task 2.1, difficulty band S2): measures time-to-first-progress,
time-to-completion, and sustained throughput across document sizes and
concurrency levels, reporting median and tail latencies, phase-separated
(upload / processing / editing / export), with a derived sizing guide.

Built by Harish for the SuperDocs Round 2 Full-Stack AI Engineer task.

## What this actually measures

Each "cycle" is a full real workflow against the live SuperDocs REST API:

1. **upload** — `POST /v1/documents/upload`
2. **processing** — `POST /v1/chat/async` (`approval_mode=ask_every_time`), polled
   via `GET /v1/jobs/{job_id}` until `status=awaiting_approval`
3. **editing** — `POST /v1/chat/{session_id}/approve`, polled until `status=completed`
4. **export** — `POST /v1/documents/export` (docx)

This exact phase breakdown is what the assigned build card asks for by name.

## Quickstart

```bash
pip install -r requirements.txt
cp .env.example .env        # fill in SUPERDOCS_API_KEY
python -m bench.main --debug-single   # one cheap cycle, sanity check
python -m bench.main                  # small-sample mode (default)
python -m bench.main --full           # full matrix — prints spend cap, asks first
```

## Real results (live run against the SuperDocs API)

`--full` was run to completion against the real API. **36 of 60 cycles
succeeded** with clean phase-separated p50/p95/p99 latencies across small,
medium, and large document tiers. Full numbers are in `SIZING_GUIDE.md` and
`bench_report.json` in this folder (generated by the run, not fabricated).

Headline numbers (p50 / p95 end-to-end, all four phases summed):

| Tier | Concurrency 1 | Concurrency 2 | Concurrency 4 | Concurrency 8 |
|---|---|---|---|---|
| small  | 7.8s / 17.0s | 8.6s / 14.5s | 13.5s / 16.5s | 11.2s / 12.8s |
| medium | 8.1s / 11.8s | 11.6s / 16.4s | 15.6s / 26.2s | 19.4s / 21.9s |
| large  | 16.7s / 19.5s | 24.4s / 28.1s | *no data (see below)* | *no data (see below)* |

**The `large` tier at concurrency 4 and 8 has no data.** Every cycle at those
two cells failed with `ConnectError: [Errno 11001] getaddrinfo failed` —
a DNS resolution failure on the machine running the benchmark, not an error
from the SuperDocs API (no request even reached the server). This benchmark
opens a fresh `SuperDocsClient` — and therefore a fresh DNS lookup — per
cycle rather than sharing one client per concurrency cell; at concurrency 8
with `large` docs (longer-lived connections, since upload+processing take
longer), that's up to 8 near-simultaneous DNS lookups hitting the local
resolver, which is a plausible bottleneck on a home network/ISP resolver.

This is being reported as a known, honest gap rather than hidden or
papered over — see "Breaking my own build" below, which the task doc itself
treats as a credibility signal, not a confession. The fix (share one
`httpx.Client` per concurrency cell instead of constructing one per cycle)
is understood and would very likely resolve it; it just wasn't applied and
re-run given the deadline. Left as a documented next step rather than
re-running blind against a fixed budget.

## What broke, and how it was actually found — worth reporting to SuperDocs

Two real API-level findings, confirmed empirically against the live service,
not assumed from the docs:

### 1. `POST /v1/chat/{session_id}/approve`'s real schema doesn't match the docs

1. First attempt (per the docs' `changes: [{chunk_id, approved}]` shape) →
   **HTTP 422**, `job_id` and `approved` reported as missing required fields.
2. Second attempt (`{"job_id": ..., "approved": true}`, satisfying that 422) →
   **HTTP 200**, `{"status": "ok", "batch_complete": false}` — but the job
   never left `awaiting_approval`, even after 120s of polling. The call was
   accepted but silently had no effect.
3. Third attempt, adding `change_id` (from `pending_changes[0].change_id`) →
   **HTTP 200**, `{"status": "ok", "batch_complete": true}` — job transitioned
   to `completed` in ~1.3s, export succeeded immediately after.

**Confirmed real request shape**: `{"job_id": <job_id>, "change_id":
<pending_changes[0].change_id>, "approved": true}`.

Worth flagging to Omkar directly: a call that returns HTTP 200 with
`"status": "ok"` but doesn't actually change job state is hard to debug from
the integrator's side — it looks like success.

### 2. A network/process crash lost 24 cycles of real data mid-run

During an earlier `--full` attempt, a transient `ConnectTimeout` on cycle
25/60 propagated as an unhandled exception and crashed the entire process —
losing every result from the 24 cycles that had already succeeded, since
nothing is written to disk until `run_benchmark()` returns cleanly. Fixed
by catching network-level exceptions at every request site (`client.py`'s
`_safe_call`) and wrapping `run_one_cycle` in a last-resort try/except
(`runner.py`) so a single bad cycle degrades to one logged failure instead
of taking the whole run down. This is what let the actual `--full` run
(above) survive its own real DNS failures at concurrency 4/8 and still
produce a complete report for the other 10 cells.

Both fixes are visible in the diagnostic logging every cycle prints
(`[bench:...]` lines) — built because a 120-second silent poll timeout on a
misconfigured request is a bad debugging experience, confirmed firsthand.

## What I cut, and why

- **No retry/backoff logic in the client itself.** A 429 or network error is
  recorded and returned as a `PhaseResult`, not retried automatically —
  retrying inside the client would contaminate the latency measurement.
  Retry policy, if wanted, belongs in a wrapper around `run_cell`, not in
  `client.py`.
- **Concurrency is `ThreadPoolExecutor`, not `asyncio`.** `httpx.Client` is
  synchronous; threads give real concurrent in-flight requests without a
  rewrite to `httpx.AsyncClient`. Verified via `load_generator_overhead_check`
  that thread dispatch overhead is negligible next to the multi-second AI
  processing latency being measured, not just assumed.
- **A fresh `SuperDocsClient` per cycle, not shared per cell.** This is the
  direct cause of the DNS-exhaustion gap above — documented as a real
  trade-off that turned out to have a real cost, not a hidden one.
- **No separate "time to first progress event" metric beyond `processing`
  phase latency.** The SSE stream (`GET /v1/chat/{session_id}/stream`) would
  give a truer "time to first token" number; this version measures time to
  `awaiting_approval` via polling instead, which is coarser but avoids a
  second transport alongside the REST polling this tool otherwise uses.
- **Doc size tiers are word-count-based, not exact section-count targets.**
  SuperDocs' actual `chunks_count` depends on its own parsing, not raw word
  count. The benchmark records the real `chunks_count` it gets back from
  each upload rather than assuming the target tier size was hit exactly.

## Files

```
bench/
  client.py    — phase-timed SuperDocs API client, network-error resilient
  fixtures.py  — synthetic document generation (3 size tiers)
  runner.py    — orchestration: small-sample mode, spend cap, concurrency,
                 graceful degradation on per-cycle failures
  stats.py     — percentile math, rate-limit exclusion, generator-overhead check
  report.py    — sizing guide generation
  main.py      — CLI entrypoint (--debug-single / default / --full)
tests/
  test_stats.py       — offline, no live key needed
  test_fixtures.py    — offline, no live key needed
  test_resilience.py  — offline, proves a cycle can never crash the whole run
bench_report.json   — raw stats from the real --full run (generated, not committed by hand)
SIZING_GUIDE.md      — the derived guide from that same run
```

```bash
pytest tests/ -v
```
