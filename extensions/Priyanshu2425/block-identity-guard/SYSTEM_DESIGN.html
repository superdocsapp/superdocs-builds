SuperDocs · open task list, band S1 · extensions folder · build note

Block identity guard

A round-trip check for SuperDocs documents. Give it the HTML SuperDocs sent and the HTML your integration sent back, and it names which blocks lost their data-chunk-id, where they are, and which transformation dropped them. Zero dependencies, no build step, no account, no network — the whole input is two strings.

The card, as printed on the open task list

Our editing model depends on each block carrying a stable identifier through a round trip. Integrations break this quietly by stripping attributes, and the failure shows up later as an edit landing in the wrong place. Build a small library that validates a document round trip and reports precisely which blocks lost identity, where, and what the likely cause was. Ship it as a package plus an optional check that can run in a build pipeline.

graded on one property: it names the specific block and the specific transformation that dropped it, rather than reporting that something went wrong

01 · what it is

A report that names the transformation

SuperDocs puts a data-chunk-id on every block-level element; those identifiers are how an instruction targets one section without touching the rest of the document. Most editor schemas and HTML sanitisers strip unknown attributes by default, so the identifier disappears quietly and the symptom — an edit landing in the wrong place — surfaces several steps later, in someone else's document. This tool closes the distance between cause and symptom.

Three ways to run it

In your editor's test suite

assertRoundTrip(incoming, editor.getHtml()) throws with the full report. This is the drop-in replacement for the three-line console.assert in the integration guide — same place in the test, an answer instead of a boolean.

As a library

checkRoundTrip(before, after) returns a report object: counts, findings, locators, causes, confidence. Pure function over two strings, so a corpus run is a map.

As a pipeline check

chunk-guard check before.html after.html. Exit 0 clean, 1 identity lost, 2 the check could not run. GitHub annotations point at the line of the captured HTML in the pull request.

The grounding, in their own docs

The integration guide's verification test is console.assert(inIds.every(id => outIds.includes(id))). It is right about when to check and says nothing about what broke. Everything in this build is the answer to the second half of that sentence.

02 · technical decisions

Every choice, and what it cost

Thirteen decisions that shaped the build, each with the alternative that was rejected. Where a decision has a price, the price is named.

Language and runtime

DecisionAlternative rejectedWhy
JavaScript, ES modules Python, matching the round's other two builds The consumers are editor integrations, and editor integrations are JavaScript. A Python package cannot run inside a TipTap, Slate, ProseMirror or Lexical test suite, which is the single highest-value place to put this check. The docs' own round-trip test is JavaScript too. Price: Node has no standard-library HTML parser, which forced the next decision.
Hand-written tolerant parser
src/parse.js, 330 lines		 jsdom, parse5, or the browser's DOMParser A dependency-free package can be vendored into any repository and run in CI without an install. More importantly, DOMParser in a browser and JSDOM in Node normalise markup differently, which would make findings depend on the environment that computed them — the exact class of bug this tool exists to catch. Price: not spec-compliant. It handles what document HTML and editor serialisers actually emit: unclosed <p> and <li>, table cells, void and raw-text elements, comments, doctypes, every attribute quoting style, and a stray < that is text.
Zero dependencies, no build TypeScript source with a tsc build A reviewer clones and runs npm test with no install and no network. Types still ship, hand-written, in types/index.d.ts. Price: no compiler checking the source; the test suite carries that weight instead.

Analysis

DecisionAlternative rejectedWhy
Match lost blocks by content Match by document position The diagnosis layer can only name a cause if it can point at what the block became, and position is the one property every one of these transformations destroys. Content is what a sanitiser, a schema and a serialiser all leave alone: the identifier is gone, the tag may have changed, the position has certainly shifted, but the sentence is still the sentence. Four passes: exact tag-and-text, text alone, similarity within the same tag (≥ 0.6), similarity across tags for text long enough to carry the match on its own (≥ 0.75, ≥ 3 tokens).
Prefer the most specific node, never reuse one First match wins A paragraph and the div wrapping it carry the same text. The paragraph is the block; the div is where it lives. Candidates are ranked by score, then by smallest subtree, and a matched node is consumed so two lost blocks cannot both claim it.
Movement measured by longest increasing subsequence Compare block indices directly Delete one block and every index after it shifts, so a literal comparison reports the whole tail of the document as moved. The longest run of blocks still in their original relative order is the document; everything outside it actually moved. One deletion now produces one finding instead of forty.
Normalise text before comparing Byte comparison No two serialisers emit identical HTML: attribute order changes, & becomes &amp;, a non-breaking space is re-encoded, whitespace is collapsed. Compared literally, every one of those is a difference and the report fills with findings about documents nobody touched. Entities are decoded, whitespace collapsed, NFC applied, and element boundaries are treated as word boundaries so two table cells are two words.
Token sets cached per node Recompute on each comparison The similarity fallback compares one lost block against every candidate, so recomputing tokens turns a linear scan into a quadratic one. Caching took the worst case — a 3,000-block document where every block was also edited — from 2.6 s to 0.75 s. Real documents hit the exact-match fast path.

Reporting

DecisionAlternative rejectedWhy
Four severities and three exit codes "Exit non-zero on any loss" The brief wanted moves reported separately and a non-zero exit on any loss; to a shell those are the same event. Severity separates them: a reorder is info and exits 0, a stripped identifier is error and exits 1, and a check that could not run exits 2 — so a missing file never reads as a pass.
Confidence and evidence on every finding State the cause as fact "Id absent, text present, tag unchanged → an attribute allowlist stripped it" is usually true and not always: an all-attribute strip and a markdown hop leave the same trace on a block whose neighbours are also bare. Findings carry high/medium/low plus the evidence, including evidence that argues against them ("this text is not unique in the after document, so the counterpart is the best match rather than the only one"). A tool that names a cause has to say how sure it is, or the next person debugs the wrong component.
Group by nearest surviving ancestor One finding per lost block One transformation usually takes a whole region. Reporting a markdown hop forty times buries the single fact worth knowing. Three or more losses sharing an ancestor collapse into one LOST_SUBTREE finding that still names every member with its own rule — so specificity survives the summarising. The group's headline rule is the one that explains most, not the most frequent: after a structural conversion the flattened containers all report as "removed", and "removed" says the least.
Baselines, with the findings still printed No baseline; or a baseline that deletes findings Run this against an integration that has shipped for a year and it finds real problems that cannot all be fixed today. Without a way to accept the known ones the check gets switched off, and a check that is switched off finds nothing. Accepted findings move out of the exit code and stay in the report, marked BASELINED. Found while writing this page: the first version printed "clean: every identifier survived" over a baselined loss. That is exactly the lie the tool exists to prevent; fixed, with a regression test.
Three output formats Human output only human for a person, json for a machine (deterministic: no timestamps, no absolute paths, stable ordering, so two runs are byte-identical and diffable), github for workflow annotations with file, line and column — a pipeline check that only writes to a log is half a check.
Golden fixture reports, committed Assertions on report fields only The report is the product, so the exact text of eleven reports is pinned in expected.txt. If a change makes any report vaguer, a test fails and the diff shows the sentence that got worse.
03 · system design

Six stages, one direction

No state, no clock, no I/O below the CLI layer. checkRoundTrip(before, after) is a pure function: the same two strings always produce the same report, which is what makes the golden fixtures possible and the JSON output diffable.

What each module owns

FileLinesResponsibility
parse.js330HTML → element tree. Tolerant tokeniser, entity decoding, text normalisation, offset → line/column lookup. Knows nothing about SuperDocs.
blocks.js159Tree → the blocks that carry an identifier, each with a locator: tag, block index, structural path, text preview, line, column, nearest ancestor that still has an identifier, and its data-part-type. Filters editor bookkeeping attributes.
match.js147Finds the after-side node a lost block became. Four passes, most-specific-node preference, token-set caching, no node matched twice.
diagnose.js216The rule table applied per lost block: which transformation, with what evidence, at what confidence. Also the document-level signals — tag-vocabulary collapse, attribute-free neighbourhoods, identifier shape.
rules.js156Every rule declared once: code, default severity, title, meaning. Plus the data attributes whose loss breaks something specific, and what it breaks.
analyse.js611The orchestrator: difference, duplicates, total-loss shortcuts, out-of-flow parts, movement by LIS, surviving-block attribute checks, new identifiers, grouping, ordering, and the stable key each finding carries.
baseline.js73Create and apply a baseline. Moves findings aside; never deletes them.
capture.js136Pulls the before-side HTML out of a saved SSE stream, one event, an array of events, or a response body. Handles focused_document_id; refuses to guess.
format/*.js206Human, JSON and GitHub-annotation renderings of the same report.
cli.js292Argument parsing, file and stdin I/O, exit codes. Injectable I/O, so the CLI tests drive it in memory instead of spawning processes.

The shape of a finding

One object per finding, identical in the library and the JSON output. This is a real one, from fixture 02:

{
  "rule": "LOST_ATTRIBUTE_STRIPPED",
  "severity": "error",
  "title": "Identifier stripped from a surviving block",
  "meaning": "The block is still there, with the same tag and the same text…",
  "id": "c1a0e0a4-0000-4000-8000-000000000004",
  "idRole": "block",
  "cause": "the tag and text are unchanged and the node kept class but no data
            attributes, which is what a sanitiser or editor schema with an
            attribute allowlist does: known attributes through, unknown dropped",
  "confidence": "high",
  "evidence": ["nearest surviving ancestor c1a0e0a4-0000-4000-8000-000000000001"],
  "locator":     { "id": "…0004", "tag": "p", "blockIndex": 4, "path": "div > p[1]",
                   "preview": "The Supplier shall indemnify the Customer…",
                   "line": 4, "column": 3, "parentId": "…0001", "partType": null },
  "counterpart": { "tag": "p", "line": 4, "column": 3, "attributes": ["class"],
                   "preview": "The Supplier shall indemnify the Customer…",
                   "hasIdAttribute": false },
  "members": [],
  "key": "LOST_ATTRIBUTE_STRIPPED:cc354ed9"
}
  • locator — where the block was, in four independent ways, so it stays findable after the file is reformatted.
  • counterpart — what the block became, or null when nothing in the after document carries its text.
  • members — populated on grouped findings; every block in the group with its own rule and locator.
  • key — stable across runs, derived from rule, identifier, path and text. This is what a baseline records.

The contract at the edges

Exit 0

Nothing at or above the failure threshold. Includes a document that was legally reordered, and a header your editor does not render.

Exit 1

The round trip lost identity. Default threshold is error; --fail-on moves it.

Exit 2

The check could not run: bad arguments, unreadable file, unusable capture. Never silent, never confusable with a pass.

04 · the rule table

Fifteen rules, each naming a transformation

The brief sketched six. Nine more came out of building it: three because the six had no mechanism behind them, and six because a checker that reports documented-legal behaviour as failure gets switched off. chunk-guard rules prints this table.

RuleSeverityTrigger, and what it means
LOST_ATTRIBUTE_STRIPPEDerrorSame tag, same text, identifier gone. The cause line distinguishes a filter that kept other data-* from one that kept only class/style.
LOST_NODE_REBUILTerrorThe text survived under a different tag. The node was reconstructed by a different document model — a serialisation round trip, not an edit.
LOST_MARKDOWN_HOPerrorCame back with no attributes at all, among neighbours equally bare, with rich tags gone from the document. Something converted the HTML to text and back.
LOST_BLOCK_REMOVEDerrorNothing in the after document carries this text or anything close to it. Deleted, replaced wholesale, or never rendered.
LOST_SUBTREEerrorThree or more losses sharing one surviving ancestor. One transformation caused all of them; every member is still named.
IDS_REGENERATEDerrorNot one identifier survived and the after document has its own. The editor set its own content instead of applying document_sync.
ALL_IDS_STRIPPEDerrorEvery identifier gone, none minted. Targeted editing is impossible; the next turn can only be a whole-document rewrite.
DUPLICATE_IDerrorOne identifier on two blocks after the trip. A change batch targeting it is ambiguous — the edit lands on whichever node the applier finds first.
DATA_ATTRIBUTE_DROPPEDerror / warnIdentifier kept, another data-* lost. Error when it is a diagram source, equation source, citation field or part marker — the report names what breaks.
DUPLICATE_ID_IN_SOURCEwarningThe input was already ambiguous. A warning about the capture, not the integration.
PART_OMITTEDinfoA header, footer, footnote or comment absent from the editor view. Documented as legal, and never destructive. --strict-parts makes it an error.
BLOCK_MOVEDinfoIdentity intact, position changed relative to the blocks that did not move. Reported so a reorder is never mistaken for a loss.
NEW_IDSinfoIdentifiers not in the before document. Normal when the user typed; called out when they outnumber the carried-over ones.
CONTENT_CHANGEDnoticeIdentifier kept, text changed. Ordinary editing; off unless --include-content-changes.
NO_IDS_IN_SOURCEerrorNothing to validate. Names any other identifier-shaped attribute it found, because this is almost always a capture taken at the wrong point.
The failure mode this table is designed against

A checker that fails a build for behaviour the platform documents as correct — an omitted footer, a reordered paragraph, a re-encoded entity — gets switched off within a week, and then it finds nothing at all. Six of these fifteen rules exist to keep legal behaviour out of the exit code while keeping it visible in the report.

05 · gaps closed

Where the shipped tool differs from the brief

The plan was a thirty-minute sketch: parse, difference, six rules, a library and a CLI. Building it surfaced problems that would have made the checker worse than useless — reporting clean when it should not, or failing a build for something documented as legal. Each is recorded in docs/GAPS.md; this is the index.

Gap in the briefWhat shipped instead
Out-of-flow parts (data-part-type) would be reported as loss — a red build for documented-legal behaviourPART_OMITTED at info, plus --strict-parts. A part that is present but stripped is still an ordinary loss.
The identifier is not the only attribute with this failure mode; diagram, equation and citation sources ride on data-* tooDATA_ATTRIBUTE_DROPPED, checked on every surviving block, with the consequence named per attribute.
Comparing raw positions reports a single deletion as a document-wide reorderMovement measured against the longest run of blocks still in relative order.
"Exit non-zero on any loss" contradicts reporting legal moves separatelyFour severities, --fail-on, and a distinct exit 2 for a check that could not run.
Matching a lost block to what it became was assumed, and it is the hard halfsrc/match.js: four passes, specificity preference, no double-matching; match quality feeds confidence.
No rule for "the block is simply gone" — a deletion would be blamed on whichever rule matched loosestLOST_BLOCK_REMOVED, reached only when nothing carries the text.
The input can already be broken, and every other finding then rests on itDUPLICATE_ID_IN_SOURCE, a warning about the capture.
"Regenerated wholesale" and "absent from a whole subtree" were listed as per-block rules; neither is oneDocument-level signals computed once, and ancestor grouping for regions.
Causes stated as fact, with no way to express doubtConfidence and evidence on every finding, including the evidence that argues against it.
Serialisation noise — entity re-encoding, whitespace, attribute order — would fill the report with false findingsNormalisation, pinned by the clean fixture.
The identifier attribute was assumed to be present and to be data-chunk-idConfigurable, with NO_IDS_IN_SOURCE naming any alternative found.
Nothing lets an existing project adopt the check without fixing everything firstBaselines, with accepted findings still printed.
No way to obtain the two HTML strings, and capturing from the wrong place gives a clean report on a broken pipelinechunk-guard capture, plus docs/CAPTURE.md naming the two ways to capture wrongly.
A pipeline check that only prints to a log is half a checkGitHub annotations with file, line, column; deterministic JSON.
The plan assumed a standard-library HTML parser, in a language whose consumers do not use itJavaScript, with a hand-written parser; identical answers on Node and in a browser.

What to look for

A reorder exits 0 and is still reported. An omitted footer exits 0 and is still reported. Both become failures only when you say they should. If either of these ever exits 1 by default, the tool has regressed into the thing it replaces.

The bug this page found

Writing this runbook is what caught it: the first version of the baseline path printed "clean: every identifier survived the round trip" over a document that had demonstrably lost one. A baseline is allowed to take a finding out of the exit code and never out of the report. Fixed, and pinned by a test that fails if the word "clean" ever appears over a baselined finding.

Step 8 · capture, the way you would in a real session

$ cat > /tmp/stream.log <<'EOF'

$ node src/cli.js capture /tmp/stream.log --out /tmp/before.html
wrote 136 characters from document_sync (document d1) to /tmp/before.html

$ sed 's/ data-chunk-id="p-1"//' /tmp/before.html > /tmp/after.html
$ node src/cli.js check /tmp/before.html /tmp/after.html
LOST_ATTRIBUTE_STRIPPED · id p-1 · confidence high          exit 1

Note what capture did not do: it read the document_sync event and ignored the final event, which also carries HTML. final is the after side of the previous turn, not the before side of this one. Ask for it explicitly with --event final.

Why exit 2 matters as much as exit 1

A pipeline that treats every non-zero as "the check failed" is fine. A pipeline that treats a crashed check as a pass is not. Everything that prevents the check from running exits 2 and says why on stderr, so the two cases are always distinguishable.

Step 11 · scale

$ node -e '
const {checkRoundTrip} = await import("./src/index.js");
let before = "<div data-chunk-id=\"root\">";
for (let i = 0; i < 5000; i++) before += `<p data-chunk-id="id-${i}" class="c">Clause ${i}.</p>`;
before += "</div>";
const after = before.replace(/ data-chunk-id="id-(1|2|3|4|5)"/g, "");
const t = Date.now(); const r = checkRoundTrip(before, after);
console.log(r.counts.beforeBlocks, "blocks,", r.findings.length, "finding,", Date.now()-t, "ms");
' --input-type=module

5001 blocks, 1 finding, ~300 ms

Five thousand blocks, five losses, one grouped finding that still names all five. The pathological case — every block edited as well as stripped, forcing the similarity fallback on every one — is roughly 0.75 s at 3,000 blocks.

08 · limits

What it does not do

Stated plainly, because a diagnostic tool that overstates its reach causes the same class of harm it was built to prevent.

It does not talk to SuperDocs

No API key, no network, no account. The input is two strings, and capture reads what you recorded rather than holding a connection open.

It does not fix anything

It names the transformation. The fix lives in your editor schema, your sanitiser allowlist, or whichever component rebuilds nodes.

It does not name the library

"An attribute allowlist", not "DOMPurify with the default config". Signature detection for named libraries was left out rather than guessed at.

Empty cells have no identity

Table cells and nested lists get a structural path, a line and an ancestor, which beats a position index — but an unlabelled empty cell cannot be matched by content, and the report drops to low confidence rather than guessing.

One document at a time

capture --document-id picks the right tree out of a multi-document session; the check itself compares a single pair.

Not a spec-compliant parser

It handles what document HTML and editor serialisers emit. Hand it a deliberately adversarial HTML5 conformance case and it will disagree with a browser.

The one number worth watching

Not the count of findings — the count of rules that fired. A pipeline losing identity in one way is a configuration fix. A pipeline losing it in four different ways is an architecture problem, and the grouped report is designed to make that visible in one screen.
