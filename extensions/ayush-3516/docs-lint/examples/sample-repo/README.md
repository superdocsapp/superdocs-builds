# Sample repository: a failing run, then a passing one

A small repository with a house style guide and one document that breaks it. The three transcripts
are real terminal output from real runs against the live SuperDocs API, committed as evidence
rather than described.

Run it yourself:

```bash
export SUPERDOCS_API_KEY=your-key-here
cd examples/sample-repo
docs-lint check -v
```

## What the three transcripts show

**[TRANSCRIPT-1-failing.txt](TRANSCRIPT-1-failing.txt)** — the first run. Seven findings, two of
them at gating severity, so the command exits 1. Both passes ran: the deterministic rules found
banned terms, Title Case headings and an unlabelled code fence; the style-guide review added a
proposal of its own. Nothing was written to the document.

**[TRANSCRIPT-2-partial-approval.txt](TRANSCRIPT-2-partial-approval.txt)** — the interesting one.
Every proposed fix was approved except the `in order to` correction, which was rejected on purpose.
Three things worth reading here:

- The rejected finding survived untouched while its neighbours were corrected.
- One fix was reported as *superseded*: two rules targeted the same heading, the first won, and the
  second said so plainly instead of failing confusingly.
- **docs-lint warned that the export changed two regions nobody approved.** Applying a style-guide
  fix means re-exporting the whole document, and the export inserted a blank line inside a fenced
  code block and split a paragraph mid-sentence. That is a SuperDocs fidelity issue, written up as
  [BUGS.md](../../BUGS.md) #10 — but a tool that promises "only what you approved changed" has to
  detect it rather than ship it silently, so it does.
- The run still exits 1 afterwards. The document does still violate the guide; declining a fix does
  not make the problem go away, and docs-lint will not pretend it did.

**[TRANSCRIPT-3-passing.txt](TRANSCRIPT-3-passing.txt)** — the reviewer repairs what the export
damaged, gives the code fence a language (no rule can guess which language it should be), approves
the last two proposals, and the run comes back clean. Exit 0, both passes recorded, and two further
model proposals dropped as no-ops because they would not have changed anything.

## The files

| File | What it is |
|---|---|
| `styleguide.md` | The house style, in plain prose. **Data, not code** — uploaded to SuperDocs once and consulted from there. Swap in your own and the linter changes with it. |
| `docs-lint.toml` | Generated by `docs-lint init`, then edited so its banned-term list matches the guide. Severities, terms and budget all live here. |
| `docs/getting-started.md` | The document under test, now in its corrected state. |

## Cost

Each run spends exactly one operation per document that reaches the style-guide review; the
deterministic rules are free. `docs-lint check -v` prints the accounting at the end of every run,
and `docs-lint report` prints it for any past run.

The `superdocs` stage took between 20 and 135 seconds across these runs — worth knowing before
putting it on a pre-commit hook. The `docs-lint-local` hook exists for exactly that reason.
