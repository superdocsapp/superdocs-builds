# Design

## Boundaries

The maintainer owns a canonical UTF-8 Markdown file and structured release JSON. It creates a complete candidate block, records its hashes and decisions, then appends the exact approved subset. PDF and DOCX are derived artifacts. The optional publication adapter produces an intended-action plan only.

The extension does not call SuperDocs, GitHub, an LLM, or an external MCP server in its default workflow. A future adapter may use the documented `sdx` API surface, but no undocumented append endpoint is assumed. This release performs 0 live/API/billable operations and makes no external publication call.

## Durable state

Each run manifest contains the canonical and release paths, release ID, input SHA-256, historical-prefix SHA-256, expected canonical SHA-256, candidate-block SHA-256, approved-block SHA-256, stable item IDs, decisions and feedback, checkpoints, output hashes, and stop-rule settings. Manifests live in a `0700` state directory and are atomically replaced with mode `0600` files.

The state transitions are:

```text
previewed → decisions_recorded → append_started → appended → export_started → completed
```

Rejected-only runs finish as `completed_no_change`. A failure after `append_started` compares the current canonical hash with the recorded post-append hash before deciding whether recovery can continue. A conflicting hash stops with an actionable stale-state error.

## Byte preservation and concurrency

The parser records marker offsets but never rewrites historical text. Before append, the workflow reacquires the canonical lock and rereads the file. If its hash differs from the preview hash, the update stops. The lock is an exclusive adjacent file with bounded waiting and dead-owner recovery. Same-file updates serialize; different canonical paths have different locks.

## Stopping and self-trigger rules

The default maximum is ten sequential releases. Preview refuses an eleventh release until an operator changes the documented policy. Preview also refuses a release whose metadata says it was generated by this maintainer, or whose path is the canonical output itself. The publication plan is never treated as a new release input.

## Reuse boundary

The implementation mirrors verified `sdx` behavior for explicit approval and structural export validation and mirrors the Release Readiness Analyst for provenance, checkpoints, and incremental revisions. No source files, dependencies, credentials, or runtime state are shared with those projects.
