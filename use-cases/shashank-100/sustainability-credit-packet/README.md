# Sustainability Credit Documentation Packet

Assembles a green-building certification submission on the SuperDocs API.

A sustainability lead at an architecture practice pursuing LEED certification
has the same problem on every project: the numbers live in spreadsheets, the
evidence lives in folders, the narratives live in Word, and the three drift
apart. Change one credit's status and you must remember to update the
scorecard, the narrative, and the evidence index by hand — or ship a
submission that contradicts itself.

This tool assembles the packet and keeps it consistent. Per pursued credit it
produces the credit narrative (written against the rating system's actual
requirement text), the calculation with its inputs shown, an evidence index
generated from what is genuinely in the bundle, and a status flag. The
submission assembles as a multi-document bundle behind a scorecard cover.
Changing a credit's status updates the scorecard and the narrative together,
in one batch a human approves.

> Built for the SuperDocs Round 2 engineer task. The project, the client and
> every document in `corpus/` are fabricated — see "Invented data" below.

## Three things it refuses to get wrong

**Narratives are written against the attached requirement, not from memory.**
The requirement text is uploaded as a source document and quoted. Anything it
does not support is flagged `[GAP: not supported by the attached requirement]`
rather than invented from general knowledge of LEED.

**The evidence index cannot lie.** It is generated by walking the bundle, not
from a hand-maintained list. Delete a supporting file and the index says so and
the credit's status flips to *evidence outstanding* on the next build. A credit
whose evidence is incomplete claims zero points, however good its arithmetic.

**The model never does arithmetic.** Every figure — fixture flow calculations,
energy cost improvement, waste diversion, scorecard totals, certification band
— is computed in `calc.py` and passed to the model already correct, with an
instruction to reproduce it exactly. Language models are unreliable at
arithmetic and worse at keeping it right across successive edits, and this
build is graded on the scorecard being correct *after* edits.

## How to run it

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

cp .env.example .env        # then add your key from use.superdocs.app
.venv/bin/python -m pytest tests/ -q          # 63 tests, no API key needed
```

The test suite runs green without a key or a network connection: the
arithmetic, the evidence resolution, the status derivation and the response
parsing are all covered against fixtures.

To build a packet against the live API:

```bash
set -a && . .env && set +a
.venv/bin/python -m packet_cli build --credit WEc1
```

## What it uses from SuperDocs

| Surface | How |
|---|---|
| Attachments | Requirement text and project evidence uploaded as source documents |
| Chat editing | One instruction per packet section, applied to the open document |
| Review | `approval_mode: ask_every_time`; every section waits for a human decision |
| Multi-document | Scorecard and narratives in one session, edited together |
| Export | Finished packet out as DOCX, PDF, or plain text |

`.csv` is not an accepted upload format, so tabular evidence (fixture
schedules, hauler logs) is rendered to Markdown first — losslessly, every row
preserved. See `sources.py`.

## Invented data

Meridian University Health System, Halloran Sterne Architects, Calloway Energy
Analytics and every person named in `corpus/` are fictional. Flow rates, energy
costs and waste tonnages were fabricated to be internally consistent and to
land on real LEED thresholds; they describe no actual project. The LEED
requirement extracts in `corpus/leed/` are paraphrased summaries written for
this exercise, not USGBC's published text.

## Notes for anyone building on the same API

`docs/BUGS.md` records what tripped me up, with reproductions — the approval
gate that does not engage on full-document writes, approval decisions that
must be keyed by `change_id` rather than the documented `chunk_id`, the job
status endpoint's real path, and why verifying a document's contents through
the chat endpoint will mislead you.
