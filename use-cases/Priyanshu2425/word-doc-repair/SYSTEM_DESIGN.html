Salvage — System Design

How the DOCX repair tool is built, and why each part is shaped the way it is. Assigned build B of the SuperDocs engineer round, band S2 · API + export. Every trade-off below cost something; what it cost is stated next to what it bought.

1  The shape

One engine, two front doors, and a styling pass inside the recovery. The engine has no dependencies at all — not FastAPI, not an HTTP library, nothing. That is what lets the same code answer a web request, a terminal, and a test suite that runs with nothing installed.

Why the engine has no dependencies

It buys three things. The test suite runs on a bare checkout, so a reviewer can check the claims without installing anything or spending a cent. The CLI works where FastAPI is not installed. And the failure surface of the thing that touches somebody's only copy of a document is as small as it can be made.

It cost the multipart encoder in superdocs_client.py, which is thirty lines that requests would have given away — and getting it wrong is invisible, because the request still sends and the API answers 422 for a field it never received. That was BUG-015.

2  The engine — how a broken DOCX is opened

A .docx is a ZIP of XML parts, and it breaks in a handful of recognisable ways. The central insight is where the damage lands.

ModuleIts one jobThe judgement in it
salvage.pyGet at the parts, going around the index rather than through it Repairs bare &, invalid characters and tags left open by a cut. Never reorders and never invents.
docx.pyRead blocks out of a body; write a valid document back Headings, paragraphs, tables and images are the only shapes it knows. Everything else is text.
media.pyFind the pictures and work out where they belonged An image whose position did not survive goes at the end under a heading, never somewhere plausible and wrong.
engine.pyThe order of the decisions, and the report Nothing is claimed as recovered before it has been read; nothing is written before everything that could refuse has had its chance.

3  Stages, and why they are branch points

Each stage is a real decision whose outcome changes the path, not a label painted on a fixed script. Two of them can refuse outright, and one falls back to a lesser result that the report is then required to disclose.

open       → salvage_members()          may refuse: no readable parts
inventory  → what is here, what can be rebuilt
                                        may refuse: the document part is gone
xml        → repair_xml()               repairs faults, closes open tags
read       → read_blocks()  ──┐         may refuse: no readable content
                              └─ on failure ─→ text_runs()  ← the fallback
                                 structure_preserved = False, and the report SAYS SO
place      → pictures the body could not be shown to reference → end, under a heading
asides     → footnotes, headers, footers → end, each under its own heading
count      → what actually came through
write      → write_docx() + preview_html
done
Why the fallback is disclosed rather than smoothed over

"We recovered your text but lost your tables" and "we recovered everything" must not look the same to the person getting the file back. When read_blocks fails, the run-by-run fallback still returns the words — and the report gains a line saying the headings, tables and formatting are gone. Finding that out later is the failure this tool exists to prevent.

Why footnotes go to the end rather than into the body

They live in their own parts, so they survive exactly the damage that destroys the index. But a footnote read as a paragraph changes what the document says, and a page header repeated inline reads as something the author wrote. They are set down at the end, labelled, and the report states they are not where they were.

4  The SuperDocs path — the four calls

The card is banded API + export. The brief's minimum contract is upload · chat · approve · export. This build makes three of them — upload · chat · export — with a balance read in front and a content check behind. The synchronous /v1/chat applies its edit inline, and the documented approve endpoint exists only on the asynchronous path; the check behind the call does the work approval before it would have done, on the file that actually ships. See D1 in BASELINE.md.

The three named traps, and where each is answered

TrapWhat it doesAnswered in
1 · the double parse Proposed-change content arrives as a JSON-encoded string needing a second parse. Miss it and every field reads undefined. parse_proposed_changes(). And pending_changes() above it, because two shapes are real: GET /v1/jobs/{id} returns a plain list, the SSE event returns the envelope. The copy that handled only the envelope crashed on the shape polling actually returns.
2 · silence is not a crash Large documents can take minutes with nothing visible happening. poll_job() treats a long quiet run as still processing and gives up only at an explicit deadline, reporting how long it waited. The page says "a quiet wait is normal" — measured at 27 s on a four-paragraph document.
3 · the allowance Work started without checking the balance fails halfway. allowance(), before the first billable call. A balance that cannot be read is not treated as zero — whoami answers agent keys, and refusing on a number nobody read would be its own bluff.
Why HTML goes up and not the rebuilt .docx bytes

The documentation is explicit that SuperDocs takes documents and HTML and that there is no endpoint for raw Word XML. Clean HTML built from structure already parsed is both supported and lossless in the directions that matter: headings stay headings, tables stay tables.

Corrected 2026-08-26. This section used to record that pictures did not make the trip, because the pass sent HTML and blocks_to_html dropped every image on the way out (BUG-094). The rebuilt .docx is sent now instead: the documented upload extracts images to cloud storage and the export preserves embedded images, so the pictures travel with the file and no separate image call is needed. Verified live — the styled file comes back carrying word/media/image1.png byte-for-byte. The guard behind the call counts them and refuses a styled file that returns with fewer.

5  The content guard

The single most important thing in this build, and it exists because of what happened on the first live run.

What went wrong

A four-line recovered report was sent up with the instruction "do not add, remove or reword any content — only restore its formatting". It came back with 199 words that were never sent: three paragraphs of invented commentary, a Subtotal / Tax / Total block, a "Remarks & Disclaimers" section, a signature block, an organisation field and a "Confidential — Internal Use Only" footer.

It opens cleanly. It reads better than the plain rebuild. That is precisely why it is the worst output this product can produce — its owner has no reason to doubt it, and may circulate it.

content_drift(sent_html, got_docx) -> (added, removed)

  _words(html)      strip tags, unescape entities, lowercase, [a-z0-9]+
  docx_text(blob)   the <w:t> runs, joined
  Counter(before) vs Counter(after)      multiset, not sequence

  added + removed > ALLOWED_WORD_DRIFT (= 0)   →   discard, and say so
DecisionRationale
Threshold is zero, not a small tolerance A formatting pass has no reason to change a single word. A tolerance would be a number chosen to let something through, and the thing it would let through is text its owner did not write.
Multiset, not sequence Reordering a table's cells is not this guard's business. Inventing a paragraph is.
Both the instruction and the guard The instruction was tightened at the same time and the re-run came back identical — but the instruction is the request and the guard is the promise, and only one of them is a test.
Rejection is safe here Discarding costs the person nothing: the plain rebuild is already downloaded and unaffected. That asymmetry is what makes a zero threshold reasonable rather than brittle.
The page says "Thrown away", not "Failed" Nothing failed. A claim was refused, and the difference is what the person needs to understand about their file's safety.

Measured: the rewritten export scores (199, 0) and is rejected; an unchanged rebuild scores (0, 0) and is accepted. Both are tests — a guard that rejects everything is an off switch, so the accept case is guarded as carefully as the reject case.

7  State, concurrency and retention

ConcernHow it is handledWhy not otherwise
Where results live An OrderedDict in memory: 30 minutes, 32 most recent, evicted oldest-first. The file someone uploads is their damaged document. Keeping it on disk is not ours to do — and a repair tool that leaks documents is a worse product than one that forgets them.
Repeat downloads Allowed. Entries are not one-shot. The first version dropped the file on the first click, so the second attempt 404'd and their only copy was gone. Clicking twice is the most ordinary thing a person does.
Concurrency Each repair runs on its own worker thread with its own queue; nothing is shared but the results dict. The engine is pure — bytes in, a Repair out — so two runs cannot interfere. There is no shared parse state to corrupt.
Progress Streamed as newline-delimited JSON, pushed from the engine as each stage happens. A page that animates a bar after the work has already finished is lying to the person watching it.
The styled copy's token A second entry in the same store, with its own token and its own filename. Overwriting the first would take away the one thing this product actually promised.

8  Trade-offs, with what each one cost

DecisionBoughtCost
Local rebuild is the default; SuperDocs is opt-in Answers "did anything survive" in milliseconds, offline, with no account and no third party holding a private document. The default file is plain. A user who wants styling has to ask for it and wait.
Engine has zero dependencies Tests run on a bare checkout; the CLI works anywhere; a small failure surface around somebody's only copy. A hand-written multipart encoder, and the class of invisible bug that comes with one.
The frontend bundle is committed A reviewer with no Node still gets the product, in one command. It can fall behind its source. Paid for with a hash manifest and a pytest that recomputes it — stale bundle, failed build.
The client is vendored into both builds Each build stands alone in the public repository, which is what the contribution rules ask for. Real drift, twice. A fix landed in one copy and not the other (BUG-015), then an improvement did (BUG-056). Paid for with a guard that fails the build when the two diverge.
Formatting changes are approved automatically A consumer is not asked to adjudicate a diff they have no way to judge. It is a gate that does not gate. Paid for by the content guard, which is the check that actually protects them — and by saying it plainly on the page rather than implying a human reviewed it.
Progress is streamed, not polled Stage lines appear as they happen, over one connection. A dropped connection loses the run. Handled: the page says so, and says the original was never changed.

9  Limits, stated rather than discovered

  • The rebuilt file is deliberately plain. Your theme, fonts and spacing cannot be recovered from a broken file, so it rebuilds clean rather than guessing at a design you had.
  • Pictures come back; captions, wrapping and floating positions do not.
  • Footnotes, headers and footers come back as text, not as page furniture.
  • Comments and tracked changes are not recovered.
  • .doc is not supported. The pre-2007 binary format is not a ZIP at all, and is reported as unrepairable rather than silently mangled.
  • Direct upload only, so the practical ceiling is about 20 MB.
  • Single process, memory-backed. Results do not survive a restart and do not span replicas. For a tool someone uses once, in one sitting, that is the right size — and it is stated here rather than left for somebody to find behind a load balancer.
