## Assumptions

| Date | Ambiguity | Call made | Reasoning |
|---|---|---|---|
| 2026-08-13 | Brief says "10-15 concrete, checkable rules" but does not say how a violation is counted. | Violations counted per instance, not per rule-broken-at-all. | Per-rule binary scoring throws away magnitude: a document with 40 contractions and one with one contraction would score identically, and the curve would flatten out early. |
| 2026-08-13 | "Checkable" does not say by what. | Each rule carries an explicit detector: 13 of 14 house rules are deterministic (regex or committed procedure, no model call); only H3 uses model judgment. | A metric that depends on a model's mood is not repeatable. Deterministic detectors also cost nothing and cannot drift between arms. |
| 2026-08-13 | Regexes for H1 (Oxford comma) and H8 (contractions) have known false-positive modes (adverbial commas; possessive 's). | Documented the false-positive shape in the rubric file, added a guard, and constrained corpus generation to avoid the ambiguous constructions. Fixture tests must pin both true and false positives before any scored run. | The alternative — a vaguer rule — moves the imprecision somewhere it cannot be seen. A documented, bounded false-positive rate applies equally to both arms and so does not bias the comparison. |
| 2026-08-13 | Whether client A (Northwind) should share the house rubric's rules. | Northwind differs from Meridian on person (L7), citation style (L11), and exclamation marks; it coincides with Meridian on the Oxford comma, sentence-case headings, "percent", dates, and contractions. | Full independence was not achievable while also keeping every axis mutually exclusive with Ember. Handled instead by classifying leak fingerprints as strong/medium/weak — see the leakage decision below. |
| 2026-08-13 | Whether corpus documents are fabricated. | Yes — all three clients and all corpus documents are fictional, per the Rails section. | Stated up front in each rubric file so it cannot be lost later. |

## Decisions

| Date | Decision | Cost | Buys |
|---|---|---|---|
| 2026-08-13 | **H3 (passive voice) stays in the rubric**, tagged `llm`, scored by a fixed committed prompt (`checker/prompts/h3_passive_v1.md`) at temperature 0, and reported as its own column separate from the 13-rule deterministic subset. | One model call per document per arm; the noisiest rule in the set; a known over-fire on adjectival participles ("is required", "was founded in 1997"). | A house-voice rubric with no voice rule is hollow — active voice is the kind of correction a real editor actually makes, and dropping it would make the metric measure only mechanical typography. Reporting it separately means the curve can be read with and without it, so the noisiest rule can never be mistaken for the signal. Operator approved this split explicitly. |
| 2026-08-13 | **Cap = 5 violations per rule per document**, AND the uncapped raw count is logged alongside it, per rule per document. | Two numbers to carry through every aggregate, chart, and raw-data file instead of one. | The cap stops one runaway rule from becoming the whole correction count (theoretical max drops from unbounded to 70/document). But a cap also compresses how large an early improvement looks: a document going from 40 contractions to 6 shows as 5→5 capped, i.e. no improvement at all. Logging both makes that compression visible instead of silent — the same discipline as reporting variance and tail behaviour rather than only the mean. Operator addition. |
| 2026-08-13 | **Checker prompt is fixed, committed, versioned, and immutable after first scored use.** `checker_prompt_version` recorded in the rubric next to the detector spec; changing a prompt requires a new version file, a new rubric version, and re-scoring of all prior documents before any cross-version comparison. | Cannot fix a checker-prompt flaw mid-run without discarding or re-scoring prior results. | A scorer that changes during a run produces a curve that measures the scorer, not the agent. This is the exact "whoever's scoring got looser" objection the brief names. |
| 2026-08-13 | **Checker is blind to the arm.** It receives only document text and a rubric id — never the arm label, run id, document ordinal, client id, prior scores, or the editing agent's transcript. Documents are submitted shuffled, under content-hash filenames. | A shuffling and hashing step between the edit run and the scoring run; scores must be joined back afterwards. | Blinding by construction rather than by good intentions. Content-hash filenames also close the side channel where an ordered filename leaks the arm. |
| 2026-08-13 | **Checker verifies each quoted passive clause appears verbatim in the source** and uses the verified count, not the model's own `count` field. | One string-containment pass per returned clause. | Stops a hallucinated count from inflating a document's score. The model must produce evidence, not a number. |
| 2026-08-13 | **Leak fingerprints classified strong / medium / weak**, with the headline leakage metric reported on the strong set only (day-first dates, third-person reader reference, ISO currency prefixes, footnote markers — and the mirror set for the other direction). | A leak on a weak axis alone will not be claimed as a leak, so the test is less likely to fire. | A hit on "Oxford comma appeared in Ember's output" is not evidence of leaked memory — base models produce Oxford commas unprompted. Claiming it would be a false positive dressed as a result. The strong set contains forms a base model has no reason to emit in consumer copy. |
| 2026-08-13 | **Leak test gets a noise floor too**: each client's corpus is scored for the opposing client's fingerprints with `cross_session_memory` OFF before any leak claim is made. A leak is claimed only where the memory-on rate exceeds the memory-off base rate. | An extra scoring pass per client (no SuperDocs operations beyond the arm that already runs). | Without it, "we found two Northwind markers in Ember's output" is uninterpretable — the base rate might be two. Same logic as the main curve's noise floor. |
| 2026-08-13 | **Fixture expectations hand-computed before the checker was run against them**, committed in `tests/fixtures/expected.json` with a note forbidding fitting them to output. Every fixture asserts a **full 14-rule vector**, not just its target rule. | Slower to author; any expectation change now needs a justification here. | Reading expectations off the instrument validates nothing. Full vectors catch detector cross-talk — a rule firing on another rule's fixture — which single-rule assertions would miss entirely. |
| 2026-08-13 | **Mutation-tested the checker suite**: seven deliberate defects injected into a scratch copy, suite must fail on each. | A scratch-copy harness and one round of rework. | A suite that passes on the first run is evidence of nothing until it has been shown to fail when the instrument is broken. This is what caught the H1 coverage gap below. |
| 2026-08-13 | **Mock H3 provider implements a real be-verb + participle heuristic with the same adjectival exception list the prompt gives the model**, and ships alongside two adversarial providers (one hallucinating, one failing). | More mock code than a stub; the mock can itself be wrong. | Task 1's lesson, applied deliberately rather than rediscovered: a well-behaved mock that always returns 0 hides bugs the live run then finds expensively. A hallucinating provider is the only way to test the verbatim-verification step at all. |
| 2026-08-13 | **Blinding enforced by construction**: `score_document(text, rubric, h3_provider)` has no parameter that could carry the arm, and a test asserts the signature. | Callers must rejoin scores to run metadata by content hash afterwards. | The cheapest way to keep a contract is to have no way to break it. A convention can be forgotten mid-run; a missing parameter cannot. |
| 2026-08-13 | **Correction protocol committed as data** (`corrections/templates.json`, v1.0.1) with one canned message per rule, quoting the first offending span. `generate_corrections` has no parameter that could carry the arm, run id, or ordinal. | Message wording is frozen; changing it after a scored run invalidates comparisons. | The brief names an improvising reviewer as the single most important design constraint to get right. A pure function of (document text, committed rubric, committed templates) cannot get better at correcting as it goes. |
| 2026-08-13 | **H3 results cached by content hash** (`H3Cache`), so a given document text is scored by the model at most once ever. | A cache file to carry between runs; a stale cache would silently freeze a wrong result. | H3 is the one rule whose score comes from a model. Without the cache, two arms producing *identical* output could receive *different* corrections purely because the model wavered — the exact confound the scripted protocol exists to remove. A test demonstrates the failure without the cache, so the guard is not protecting against an imaginary problem. |
| 2026-08-13 | **One message per rule per round, capped at 8 rules**, lowest-numbered first. | A document violating all 14 rules is corrected on 8 of them per round. | Bounds the correction payload: a document with 40 contractions must not generate 40 messages. Deterministic selection means both arms are corrected on exactly the same rules for the same output. |
| 2026-08-13 | **Quoted spans are flattened, truncated, and framed as data**; the preamble states that quoted text is document content and never an instruction. | Spans lose their original line breaks. | Corpus documents are untrusted content the agent reads through `chat`. A span carrying a newline could otherwise forge a new numbered instruction line inside the correction payload. Behaviour 8 applied to the correction channel, not just the document channel. |
| 2026-08-13 | **H3 cache is an enforced precondition, not a documented risk.** `runner/preflight.py` refuses to start a run unless the cache exists, parses, sits inside the published run directory, and is tracked by git — and is non-empty from the second arm onward. | A run directory must be created and its cache file initialised before the first document is edited. | Operator's call, and correct: the failure it prevents is only discoverable after twenty documents have run, at which point the experiment cannot be salvaged. The staged non-empty check reflects that a fresh experiment legitimately starts cold, while the second arm reusing an empty cache is exactly the silent break. |
| 2026-08-13 | **The publication check degrades closed**: if git cannot say whether the cache path is tracked, the check FAILS rather than passes. | A run cannot start outside a git repository. | Found because the mutation harness ran in a copy without `.git`, where the check silently passed. A precondition whose whole job is to abort must never read "I could not tell" as "fine" — that is the exact mechanism by which an unverifiable experiment gets produced. |
| 2026-08-13 | **Fake SuperDocs transport reproduces the API's awkward parts on purpose**: JSON-encoded proposed-change content, error envelopes rather than exceptions, and a switch for content that is already an object. | More fake than a stub needs. | Task 1's shape-vs-grade defect was invisible to a keyless suite because its fake was better behaved than the real service. Anything this fake makes easier than reality is a bug in the fake, and it is documented as such in its own docstring. |
| 2026-08-13 | **The second parse is the last one** — `parse_proposed_content` never loops until the value stops being a string. | A triple-encoded payload would not resolve. | Both failure directions are real. Parsing once too few leaves a string where an object is expected; parsing once too many silently corrupts a change whose text happens to be `"[1, 2]"` or `"true"`. The documentation says the final result is already an object, so the loop is wrong even though it looks more robust. |
| 2026-08-13 | **Client refitted to the observed API**, not the brief's minimum contract: `session_id` (not `document_id`), `file_base64` (not `content_base64`), `document_changes` (not `proposed_changes`), `approve_change` requiring `change_id`. | A rewrite of the client, its fake, and its whole test file. | The first version passed 167 keyless tests while being unable to work against the real service, because the fake shared the client's wrong assumptions. Contract tests now run against **real captured responses** in `tests/fixtures/real_responses/` — a fake can agree with a wrong assumption, a captured payload cannot. |
| 2026-08-13 | **Retries are free, and the retry policy says so explicitly.** `chat_with_retry` retries transport failures and no-op chats, counting them as `free_retries` in the ledger. | Retries cost latency and can mask a persistently failing prompt. | Measured: an errored chat and a chat producing no edit are both billed 0; only an applied edit is charged. So reliability and budget are not in tension here, and the policy should not be written as though they are. Counting free retries separately keeps that visible in the run report rather than implied by the cost table. |
| 2026-08-13 | **The measurement uses synchronous `chat` with `approval_mode: approve_all`**, not the async job + `approve_change` path. | The explicit approval step is exercised by tests and a live demonstration, but is not on the measurement path. | Two measured reasons. First, only the synchronous response carries the `usage` block, so the async path gives **no billing telemetry at all** — the ledger recorded 0 operations for a run that genuinely applied edits. Second, the async path returned 7 of 10 proposed changes as no-ops (`old_html == new_html`) and applied nothing on a full correction payload, while the sync path took the same document from 24 violations to 9. |
| 2026-08-13 | **`cross_session_memory_key` is the per-customer isolation primitive; `cross_session_scope` is a list of SESSION ids restricting search.** | The leakage design has to be restated in these terms. | Read off the live tool schema. The earlier design used `cross_session_scope` as the customer scope, which would have made the leakage test meaningless — it would have "isolated" clients using a parameter that does not isolate anything. Caught before the leak test was built. |
| 2026-08-13 | **`cross_session_memory_key` is the sole customer-isolation primitive; `cross_session_scope` is used nowhere in this design.** Confirmed against the live tool schema and a live isolation probe. | The earlier design used `cross_session_scope` as if it were the customer boundary. | Schema, verbatim: `cross_session_memory_key` — "the cross-session memory note is kept in a **separate file per end-customer**." `cross_session_scope` — a session-id allowlist that "**only narrows within the API-key owner**", and is "ignored unless `cross_session_search` is on." Scope restricts search, not memory, and does not partition by customer at all. Using it as the isolation mechanism would have made the leakage test meaningless — it would "isolate" clients with a parameter that isolates nothing. Caught before the leak test was built, per the operator's explicit priority. |
| 2026-08-13 | **`cross_session_search` is never enabled, in either arm or the leak test.** | The "search past sessions" capability described in TASK.md's memory primitives goes unused. | Schema, verbatim: `cross_session_search` "may search your PAST chats and documents on demand to reuse prior work and **open a found document**." This is not the style-note mechanism at all — it is a different, riskier capability that can surface content from other sessions account-wide, and `cross_session_scope`'s "only narrows within the API-key owner" means it cannot be used to bound search to one customer's key. Turning search on would be a leak vector, not a leak defence, for a feature the brief's stated mechanism (a durable note) does not require. |
| 2026-08-13 | **Live isolation probe, before building on the assumption.** Taught a fact under `memory_key=X`; a fresh session under the same key, a different key, and no key all failed to recall a bare "remember this" instruction — the write path is not triggered by an arbitrary chat message. A second probe using a real edit+scripted-correction cycle (the actual protocol) showed the correction applied correctly within the teaching session, and a fresh session under a **different** key showed no trace of it. | ~6 live operations. | The schema's isolation claim is now independently observed, not merely read. The negative result on same-key recall via a bare instruction is not evidence memory is broken — it's evidence that a "please remember X" message doesn't route into the note store the way an actual edit/correction cycle does, which is consistent with the product's stated design (learn from real editing history) and is exactly what n=3 exists to test properly with the real protocol. |
| 2026-08-13 | **The generic edit instruction had to be rewritten before any document could be scored.** The original wording ("Edit this document to match our house style") reliably produced a clarifying-question response and **zero edit**, independent of memory state, on a document with no further context. Replaced with a directive instruction that forces an edit attempt without naming any rubric rule. | None — this is a correctness fix, not a scope trade. | If the agent declines to edit, `export_document` returns the unedited source and the checker would score the **injected violation profile**, not "the agent's output" — the metric becomes undefined for that document. Verified 3/3 live trials with the revised wording produced a billed edit. The rubric is still never disclosed; only the instruction is more forceful about requiring an attempt. |
| 2026-08-13 | **H3's real provider wired**, reading the committed `checker/prompts/h3_passive_v1.md` prompt verbatim and substituting only `{{DOCUMENT_TEXT}}`. Verified live against a 3-sentence fixture: found exactly the one true passive, correctly excused the adjectival-participle exception ("is required"). | One more live-call surface to keep in sync with the prompt file. | This was a stub until now (`NotImplementedError`, by design, so the keyless suite never depended on it). The blinding contract — no arm, run id, or client id ever enters the prompt — lives entirely in the prompt file, so wiring the real call required no new blinding logic. |

Pinned by a regression test using a provider that fences its response, the shape a mock without this property would never exercise. |
| 2026-08-13 | **Gemini calling logic extracted to `gemini_client.py`**, shared by the corpus prose stage and the real H3 provider. | One more shared module. | Two independent call sites for the same external API were about to diverge (SSL context, endpoint, request shape) the moment H3 needed a real implementation. One source of truth instead. |
| 2026-08-13 | Rubrics committed as **data** (`rubrics/*.json`) with detectors, guards, examples, and documented false-positive modes inline. | Verbose files. | The brief requires the style guide be committed as data, not inferred by feel. Examples and known failure modes travel with the rule so the checker implementation and the fixture tests are pinned to the same spec. |

## Confirmed operation costs (measured 2026-08-13, meter probe)

These replace the assumed cost model in full. Raw data: `runs/meter_probe/probe.json`.

| Call | Measured cost | Evidence |
|---|---|---|
| `chat` — document actually edited | **1 op** | three sequential edit chats: 9,994 -> 9,993 -> 9,992, `ops_charged: 1` each |
| `chat` — no edit produced | **0 ops** | `was_billable: false`; three consecutive reader chats left the counter flat at 9,990 |
| `chat` — `cross_session_search: true` | **1 op** (no surcharge) | 9,992 -> 9,991, `ops_charged: 1` |
| `chat` — errored (HTTP 422) | **0 ops** | next reader showed a delta of exactly 1, attributable to its own edit |
| `init_session` | 0 ops | 7 non-chat calls bracketed by two reader chats: promo delta 0 |
| `upload_document_base64` | 0 ops | same bracket |
| `export_document` | 0 ops | same bracket |
| `request_download_url` | 0 ops | same bracket |
| `clear_cross_session_memory` | 0 ops | same bracket |
| `list_documents`, `get_document_detail` | 0 ops | same bracket |
| `get_account_status` | 0 ops | null probe: two reads, delta 0 |

**The instrument was wrong and had to be corrected mid-probe.** The first counter — `get_account_status.quota.used` — reports the *free-tier monthly bucket* (500/month). Charges draw from the **BUILDER26 promo bucket** (10,000 granted). That counter stayed flat at 5 through every billable call, so the probe's first pass reported every cost as 0. The correct instrument is `usage.promotions[0].ops_remaining`, returned inside the chat response. Had the probe been trusted at that point, the budget would have been built on the claim that everything is free.

**Billing is a property of the edit, not the call.** A `chat` is billed only when the document actually changes; the service reports this per response as `was_billable` / `ops_charged`. The ledger now reads that reported number instead of inferring cost from the tool name.

**A no-edit chat is a free counter read.** It costs 0 and still returns the promo balance, so the run can monitor its own budget continuously at no cost. This is the only free way to read the promo bucket — `get_account_status` does not report it.

## Known limitations

- The metric measures **rubric adherence**, not editorial quality. It is a proxy for what a human editor would flag, not the thing itself. This is stated in the write-up, not buried here.
- H3 (passive voice) over-fires on adjectival participles and is the only rule dependent on a model call. Reported separately for this reason.
- H1 (Oxford comma) can fire on sentence-initial adverbial commas; H8 (contractions) cannot fully disambiguate possessive `'s`. Both are guarded, both are documented in `rubrics/meridian.json`, and corpus generation avoids the ambiguous constructions. The residual error applies equally to both arms.
- E9 (Ember full-sentence bullets) uses a finite-verb heuristic — the one soft edge in the client rubrics.
- Proper-noun handling in H2/N2 depends on a fixed allowlist. Corpus generation must not introduce proper nouns outside it.
- **Checkpoint findings, 2026-08-13 — checker vs. real Gemini prose.** Scored 6/8/11 against a predicted near-zero. Every firing was inspected against the source. Two genuine checker defects, both now fixed with regression fixtures:
  - **H4 false-positived on date day-numbers.** Real prose wrote "between January 1 and March 31"; the bare `1` was flagged as a spell-out-under-ten violation. Nobody writes "January one". Day numbers are date components governed by H6, not prose numbers. `_mask_for_numbers` now masks month-day pairs in both orders. Fixture `h4_date_daynumber.md`. **This defect was invisible to 18 hand-written fixtures** and would have added a spurious violation to every document in both arms.
  - **H5 reported a truncated span.** A `30%` violation reported its span as `0%`, because the pattern matched only the digit adjacent to the symbol. Count was correct, span was not — and spans are quoted verbatim into correction messages, so every H5 correction the agent learned from would have quoted a nonsense number. Pattern widened to the whole number; count unaffected. Fixture `h5_span.md`.

The 24 injected violations are therefore packed into roughly half the intended prose. The concern is not density for its own sake: **less natural prose between injected violations means a document is easier to correct completely, whatever the agent has or has not learned.** A short document with 24 clustered errors can be brought to zero by a careful pass over a small amount of text, so the memory-on arm may reach low correction counts partly because the task is small rather than because memory transferred anything. Stated in the write-up as a limitation on external validity, not filed as a disclosed number.
